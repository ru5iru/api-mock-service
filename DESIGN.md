# Design System: MockDeck

## Overview

The supplied desktop workbench is the visual authority: warm surfaces, compact typography, continuous working areas and restrained elevation. The current implementation captures its shared frame, registry treatment, bounded endpoint workspace and response authoring while retaining the application's existing feature controllers and interaction contracts.

This is a source-derived record of the bounded foundation, registry and endpoint workspace implementation, not evidence that the full upgrade checklist is complete. The delivered frame comprises the topbar, navigation rail, contextual sidebar and statusbar; the editor sidebar adds a paginated endpoint explorer. The registry adds explicit filter captions, contextual selection actions and a secondary Recent requests disclosure. Endpoint editing now uses Editor / Callback / Settings, with Request and Matching subtabs plus Signature in the left pane and Responses in the right pane on wide screens. The response form now delivers compact parameters, a continuous Body canvas, Builder / JSON editing and an explicitly labelled sample preview. Selection, fault and Callback visual migrations remain pending in `docs/UI_UPGRADE.md`; their existing controls remain available.

Key characteristics:

- Warm light and dark themes with semantic color roles.
- Dense, readable controls and mono text for technical content.
- Flat work surfaces separated by fine borders.
- Existing native and Livewire behavior retained behind shared chrome.

The normative implementation is `public/css/tokens.css` plus the Workbench foundation, Registry workspace, Endpoint workbench and Response authoring blocks in `public/css/app.css`; `docs/UI_GUIDE.md` documents its current migration stage. Frontmatter keys prefixed `light-` and `dark-` are the resolved values of the same CSS token in each theme; they are paired alternatives, not an expanded set of unrelated colors. Component frontmatter records the default light mapping; actual components resolve theme-aware CSS variables. `.impeccable/design.json` carries motion, elevation, breakpoints and isolated component previews.

## Colors

### Primary

The warm amber accent identifies primary actions, links, focus and selected context. Use the accent family through `--accent`, `--accent-hover`, `--accent-subtle`, `--accent-border` and `--accent-link`; keep foregrounds paired with `--on-accent`. Selection and focus have their own tokens and are not interchangeable with persistent success feedback.

### Neutral

Canvas, work surface, secondary surface, raised surface and hover surface have distinct roles. Header/status chrome uses `--shell-chrome`; rail/sidebar uses `--shell-sidebar`. Text uses primary, muted and subtle roles; borders use ordinary and strong roles. Dark mode relies on warm tonal layering rather than generic black panels. Technical code surfaces retain the code palette in either theme.

Success, warning, danger and information notices each use their matching background, foreground and border tokens. Destructive filled actions use the danger-fill pair and `--on-danger`. HTTP method badges retain the existing method palettes; syntax highlighting remains defined in the token source. Color supplements visible copy and icons.

**The Paired Theme Rule.** Change the light and dark mapping together and preserve the semantic role. Do not copy prototype literals into feature-specific styles.

## Typography

The interface uses the system UI stack; technical content uses the locally supplied JetBrains Mono stack. The body is compact (13px, line-height 1.5). Page titles use the semibold title role (16px, line-height 1.25); the workbench brand uses 14px. Supporting labels and explorer identities use 12px; statusbar, compact badges and technical identifiers use 11px where already implemented. The available scale also includes 20px for existing larger contexts; the workbench does not introduce a display typeface.

Weights are regular (400), medium (500), semibold (600) and bold (700). Preserve legibility of identifiers: code uses mono, ligatures are disabled on code and identity-heavy lists, and explorer names wrap anywhere rather than losing their identity to a single clipped line.

## Layout

The frame is defined by CSS tokens: rail (52px), context sidebar (252px), header (52px) and statusbar (28px). The normal work-area offset is rail plus sidebar. The header remains at the top; rail and sidebar sit between header and statusbar; the statusbar spans the bottom. Work-area padding follows the spacing scale (20px desktop, 12px at narrow widths). Context heading/footer remain stable while the explorer can scroll.

At 1100px and below, the sidebar becomes an optional drawer and the work-area offset retains only the rail. At 767px and below, the rail disappears, the offset becomes zero, the contextual drawer starts at the left edge, and mobile navigation remains available. At 440px and below, page headers wrap their actions to avoid title/count collisions. Sidebar collapse is a presentation preference; drawer opening is temporary. Drawer Escape restores focus to its toggle. The sidebar is inert while hidden.

Sticky actions begin at the current work-area offset and sit above the statusbar. Their measured height participates in content padding. The endpoint workspace uses a measured outer viewport: above 1100px, its request form and response workspace scroll independently within two minimum-zero columns (0.95fr / 1.05fr), with no outer workspace scrolling. At 1100px and below, the panes stack in request-then-response reading order, pane scrolling is removed and the outer viewport scrolls. Settings and Callback each use a single column. Height measurement accounts for the actual header/tabs, save bar, statusbar and breathing room (16px); Signature shares the request pane rather than adding a third scroller. Existing tables and code surfaces retain their own bounded overflow.

The explorer is a flat filtered list with search and collection selection, including Unfiled. It reuses EndpointIndex and paginates 15 endpoints with its own `explorerPage` name. It is not a replacement for the full registry or a new collection tree.

The registry is a continuous workspace: full-width search, wrapping labelled filters, a contextual selection strip, page selection/result count, endpoint rows and pagination. At 740px and below, filters form two equal columns; at 440px and below, they stack into one column to preserve readable option names. At 1100px and below, row actions move below the facts; at 740px and below, the existing stacked facts/actions layout remains. Recent requests follows pagination as a secondary disclosure.

## Elevation & Depth

Working areas are flat: workbench cards, registry rows and buttons have no decorative shadow or hover translation. Registry rows touch, share one outer border and use internal separators. Depth comes from surface tone, boundaries and active state. Existing overlays and menus retain the established elevation vocabulary; dark mode removes ambient shadows. Focus/selection rings remain state indicators, including in dark mode.

Motion uses the existing short ease-out transitions (120ms and 180ms). Reduced-motion rules collapse animation and transition durations, and theme switching suppresses transitions. Do not add entrance motion to persistent shell surfaces.

**The Continuous Surface Rule.** Keep the registry contiguous and square-cornered. Use the shared hover surface for row feedback, not floating cards.

## Shapes

The reusable corner scale is small (4px), medium (6px), large (8px) and pill (999px). Most controls use gently curved medium corners; menus use the large radius; tag chips retain pill corners. Workbench cards, registry rows and the brand mark are square. Method badges retain their existing small rounded shape. Standard boundaries are fine (1px); focus outlines are stronger (2px with 3px offset).

## Components

### Buttons and fields

Primary, secondary, tertiary and destructive actions retain existing variants, labels and disabled/loading contracts. Standard buttons use 8px/16px padding, 13px semibold type and a 36px minimum height; small buttons retain their 38px variant, and the narrow-screen button rule raises the minimum to 44px. Workbench overrides remove button shadow and translation across states. Disabled controls use the disabled token pair and ordinary border.

Labelled inputs retain transparent resting surfaces, a strong border and medium corners. Ordinary text inputs use a 48px minimum height with 10px/12px padding; existing dense and schema controls keep their established geometry. Hover changes the border to the accent border; focus uses the accent border, work surface and focus shadow. Native selects and validation remain the existing shared controls.

### Navigation and context

Rail links are centered icons with accessible labels and a minimum height of 40px. The active destination retains `aria-current="page"`; hover and active share the subtle accent surface. Context links use 36px minimum rows, increasing to 44px at narrow widths. The visible sections remain Endpoints, Logs, Import / export, Environments and Documentation. Context content uses real route links rather than invented workspace features.

### Registry and explorer rows

Registry entries retain their identity, contextual details, nested actions, checkboxes and disclosures. The visual container is a continuous bordered list with 12px row padding and no gaps. Selected rows use the subtle accent surface; focus within a row adds an inset accent boundary. Custom names wrap anywhere. Copy, Edit, enable switches and More actions remain visible without hover. Switches and menu triggers have a 44px minimum hit height; the Canonical request summary has a 28px minimum height. Nested controls retain native keyboard behavior; row Enter activation applies only when the row itself is focused.

The contextual selection strip uses the subtle accent surface and accent border. It names the total selected count and the count on this page, explains that selection persists across pages and filters, and keeps existing bulk actions together. The page checkbox synchronizes native checked and indeterminate states after updates; Clear selection retains its whole-selection behavior. Add tags keeps its native menu open while checkbox drafts update the Apply tags state; assignments change only when Apply tags is activated. Bulk actions disable repeated submissions while pending.

Empty states distinguish an empty registry, an empty collection or Unfiled view, and no filter matches, with create/import or clear-filter recovery. Filtering and pagination retain the existing skeleton with a concise loading status. Recent requests starts open with a 44px minimum summary target and reuses the compact LogViewer, including polling, request detail and Pause/Resume. Collapsing it adds no stored preference.

Explorer rows use 12px/8px padding, a method badge, wrapped identity and response/enabled summary. The current endpoint is marked through `aria-current`; hover/current use the subtle accent surface. Previous/Next controls remain native buttons with true boundary disabled state. The explorer uses existing dirty-navigation handling for its links.

### Endpoint workspace

Primary navigation is Editor / Callback / Settings. Editor owns the Request / Matching subtabs and Signature on the left, plus a labelled Responses region on the right; Responses is not a fourth primary tab. Primary and nested tabs retain selected state, roving focus and Arrow/Home/End navigation. Legacy Request, Matching and Response deep links map into Editor; Callback links remain intact. Metadata validation opens Settings, signature-policy errors open Matching and raw-source errors open Request. Readiness indicators describe the current configuration and do not turn parsing success into a saved/callable-state claim.

The original endpoint-settings form owns Request, Matching and Settings, including enabled state, priority, collection and tags. Its save target, scoped validation and draft baseline remain intact; title rename stays a separate mutation. One ResponseManager is mounted as the sibling response workspace and serves both Responses and Callback. Switching tasks never duplicates the manager or nests its forms inside the endpoint form.

Responses begins with the native Response to edit picker and New response action, followed by the response form, selection settings and the full configured pool. The picker invokes the existing edit action; New response uses the existing create action. Switching preserves each response's draft, and Cancel edit discards only the current draft. Picker labels expose response identity and unsaved state, and selected state follows the active editing ID after updates. Static / Template, Builder / JSON and sample preview now share the delivered response-authoring canvas described below. Selection, fault, History and callback controls retain their existing behavior; selection, fault and Callback visual migrations remain pending. Container-width rules continue to stack condition rows to fit the pane.

Saved endpoints expose Copy mock curl and an endpoint-filtered Logs link beside the primary tabs. Copy resolves saved configuration and the active Environment on the server at action time through the existing shared copy path; unsaved request changes are excluded and resolved values are not embedded in a new page attribute. Signature explicitly labels the Source URL and draft canonical preview, keeping source identity distinct from the actual mock invocation. New endpoints retain create-before-response guidance, and endpoints without a saved response retain the existing informational diagnostic state.

### Response authoring

The response form begins with compact Status / Weight / Delay parameters, followed by the full-width Weighted-only explanation and Headers with a three-row editable viewport. One Body canvas, separated by fine block borders rather than a nested card, groups Static / Template, the active editor and the sample. Static retains its nine-row body field. Template adds a wrapping Builder / JSON toolbar with Example, followed by Locale and Seed in two minimum-zero columns; the generation settings become one column at a container width of 380px or less. Fixed seed places its existing Seed value field across the row with a 180px input maximum.

Builder is a continuous schema workspace with border-separated rows. A row places its drag handle beside key and type, configuration beneath, and nullable controls with reorder/delete actions below. Each row is an inline-size container: deeply nested rows adapt to their own available width, not the viewport. At 380px or less, fields/configuration/actions stack and action targets become 44px. Nested groups use the existing 8px spacing step to retain usable input width. These overrides are scoped to `.endpoint-response-workspace .response-form`; Callback Builder keeps its existing recipe.

JSON starts with 12 rows and a minimum height of 220px. The sample uses the existing code surface and overflow behavior with a 300px maximum for its preformatted output. Its heading explicitly says Sample data, its region retains `aria-describedby` pointing to the existing synthetic request-context notice, and the pending Regenerate action announces Rendering sample. Structured validation and quick fixes remain between the editor and preview. Preserve the existing catalog, Builder converter, rendering, locale/seed, validation and save services; unsupported structures and context tokens remain JSON-only. A preview does not persist configuration or advance runtime selection.

### Tags, notices and code

Tags remain compact pill chips using secondary surface and muted text. Notices retain semantic copy/icons and a uniform fine boundary. Code and preview blocks keep mono text, code surfaces and existing disclosure/copy behavior. Shell work must not change exact copied values, secret masking, request matching, import semantics or run isolation.

### Tooltips and preferences

Help triggers are native buttons with their existing description associations. Workbench trigger geometry is 24px; tooltip panels are hoverable, open on hover/focus and dismiss with Escape, including hover-only bubbles. Per-anchor delayed closing (150ms) permits pointer travel across the anchor gap; ordinary pointer departure closes the panel when neither anchor/panel hover nor anchor focus remains. Dismissal lasts through the current hover/focus interaction. Panel placement remains the shared implementation.

Only sidebar collapse and single-key shortcut enablement are stored as workbench preferences. The shortcut preference controls N, / and ? outside editable fields. The footer Shortcuts button remains reachable after single-key shortcuts are disabled; it uses a compact 24px target within the statusbar. Drawer state resets on navigation and breakpoint changes. Do not store configuration drafts or secret values in these presentation preferences.

## Do's and Don'ts

- **Do** use existing semantic CSS tokens and inspect both theme mappings.
- **Do** preserve full identities, real active/selected state, native controls and accessible names.
- **Do** retain the continuous registry treatment and measured sticky offsets.
- **Do** distinguish delivered foundations from unchecked feature migrations in `docs/UI_UPGRADE.md`.
- **Don't** treat the delivered endpoint workspace and response authoring as completion of the selection, fault or Callback visual migrations.
- **Don't** turn parser/preview readiness into a saved or callable-state claim.
- **Don't** add decorative card shadows, hover translation or prototype-only features to workbench surfaces.
- **Don't** change mutation, matching, import, credential or isolated-run contracts as a visual side effect.
